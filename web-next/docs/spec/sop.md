## SPEC-sop-0 模块概述

SOP 是标准工作流：把反复做的事编排成一张有向图（自动步骤、AI 步骤、判断分支、并行、人工检查点），每次按同样的步骤执行，每一步的输入输出都留在执行记录里，人可以在四个地方插手：执行前暂停（逐步确认）、人工检查、人工判断、失败后重试或跳过。给一个人做产品和运营时用，把「客户反馈转需求」「周会纪要整理」「联系人建档」这类事交给流程跑，只在需要人的地方停下。

原型里执行由前端定时器模拟（每 250ms 推一次），每种节点的产出是写死的规则，不连真服务；哪些是模拟、后端要怎么真做，见 `SPEC-sop-12`。

### 共用数据结构

`Sop`（`web-next/src/sopflow.ts`）：一条流程定义。

| 字段 | 类型 | 必填 | 说明 | 取值 / 示例 |
|---|---|---|---|---|
| `id` | `string` | 是 | 编号；新建用 `newId('sop')` | `sop_feedback` |
| `name` | `string` | 是 | 流程名；保存时不能为空 | `客户反馈转需求` |
| `desc` | `string` | 是 | 一句话说明，可为空串 | `把 IM 里的客户反馈提炼成诉求…` |
| `trigger` | `string` | 是 | 触发方式，存 `sop_trigger` 枚举的 key，显示时换成枚举的显示名，枚举里找不到时原样显示（正式产品里 `im` 是来消息自动发起，见 `docs/api-contract.md`「IM 触发」，SOP-05；`schedule`「定时」按开始节点里设的时间规则到点发起，规则存在随流程管理的定时任务里，TSK-0463）。旧的 `daily`「每天 09:00」、`weekly`「每周一 18:00」、`cron` 不再是选项，正式产品升级时转成 `schedule` 加等价规则（`SPEC-sop-12.53`），显示也按「定时」 | `manual`、`im`、`schedule` |
| `sched` | `{ rule: ScheduleRule; enabled: boolean }` | 否 | 只在编排页的草稿里：触发方式是 `schedule` 时的时间规则（同定时任务的 `ScheduleRule`，`SPEC-tasks-0`）和启停。保存时写进随流程管理的定时任务（定时任务列表里 `action.kind = sop`、`action.managed = true`、`action.sop_id` 是这个流程的那一条，一个流程最多一条），流程本身不存；打开编排页时从那一条带出来，没有那一条时为空，即「定时，未配置」（TSK-0463） | `{ rule: { freq: 'weekly', time: '18:00', weekdays: [1], … }, enabled: true }` |
| `im` | `{ conversations: string[]; relevance: ('me' \| 'all' \| 'dm' \| 'none')[]; relevance_mode: 'include' \| 'exclude'; order: number; stop: boolean }` | 否 | IM 触发的过滤条件、执行顺序与拦截（TSK-0481），只在触发方式是 `im` 时起作用；没有时是不过滤、排最后、不拦截。`conversations` 只接这些会话的消息，空为全部（原型存会话名，正式产品存内核会话 id，见 `docs/api-contract.md`「IM 触发」）；`relevance` 与我的关系（@我、@所有人、私聊、无关），空为不限，`relevance_mode` 是只要还是除了；`order` 在 IM 流程里排第几（1 起，连续）；`stop` 命中并发起后排在后面的 IM 流程不再接这条消息 | `{ conversations: ['#random'], relevance: ['me'], relevance_mode: 'exclude', order: 1, stop: true }` |
| `fields` | `SopField[]` | 是 | 执行时要填的输入；新建默认一个「输入内容」 | |
| `steps` | `SopStepDef[]` | 是 | 步骤，按依赖排好的顺序（编排页改连线后 `topo` 重排）；保存时至少一个 | |
| `layout` | `Record<string, { x: number; y: number }>` | 否 | 编排画布上的节点位置，key 是步骤 key，`__start` 是开始节点；没有就按依赖自动排 | `{ "__start": { "x": 60, "y": 180 } }` |

`SopField`（`web-next/src/sopflow.ts`）：开始节点的输入字段。

| 字段 | 类型 | 必填 | 说明 | 取值 / 示例 |
|---|---|---|---|---|
| `key` | `string` | 是 | 字段 key，执行输入里按它存 | `customer`；编排页新建为 `f<时间戳36进制>` |
| `label` | `string` | 是 | 显示名；保存时不能为空 | `客户` |
| `type` | `'text' \| 'textarea' \| 'select'` | 是 | 输入框类型 | `text` 单行 / `textarea` 多行 / `select` 下拉 |
| `options` | `{ value: string; label: string }[]` | 否 | 下拉选项，`select` 才有 | `[{ value: 'lark', label: '飞书' }]` |
| `placeholder` | `string` | 否 | 占位提示 | `联系人姓名` |
| `required` | `boolean` | 否 | 必填；发起执行时空着不让开始 | `true` |
| `default` | `string` | 否 | 默认值，发起执行抽屉里预填 | `梁晚晴` |

`SopStepDef`（`web-next/src/sopflow.ts`）：一个步骤（画布上的一个节点）。

| 字段 | 类型 | 必填 | 说明 | 取值 / 示例 |
|---|---|---|---|---|
| `key` | `string` | 是 | 流程内唯一；编排页新建为 `s<序号>` | `extract` |
| `name` | `string` | 是 | 步骤名；保存时不能为空 | `AI 提炼诉求` |
| `kind` | `StepKind` | 是 | 节点类型，18 种之一，见 `SPEC-sop-11` | `ai` |
| `desc` | `string` | 是 | 说明；在属性面板里标题随类型变（`descLabel`），AI 处理时就是给 AI 的要求 | `每条诉求给出一句话描述…` |
| `ms` | `number` | 是 | 模拟耗时，毫秒；新建取类型的 `ms` | `2200` |
| `after` | `string[]` | 否 | 依赖的步骤 key；多于一个是汇合；不写就接在定义顺序的上一步后面，`[]` 是起点。编排页里一律写明（`explicit`） | `['archive', 'bug_ticket']` |
| `branch` | `{ of: string; case: string }` | 否 | 只在判断步骤 `of` 选了分支 `case` 时才执行 | `{ of: 'classify', case: 'feature' }` |
| `run` | `(input: Json) => Json` | 否 | 原型写死的产出规则；没有时按类型的 `run` 模拟。正式产品不存函数，由后端按类型和配置执行 | |
| `fail` | `(input: Json) => string \| null` | 否 | 原型写死的失败规则，返回错误信息即失败，重试时再判一次 | 回复渠道为微信时失败 |
| `cases` | `SopCase[]` | 否 | 分支节点（`decide`、`classifier`）的分支；至少两个 | |
| `decide` | `(input: Json) => { route: string; reason: string }` | 否 | 原型写死的判断规则（只有示例流程有） | |
| `rule` | `string` | 否 | 条件分支的判断规则描述；`decide` 和 `rule` 都没有（或 `rule` 为空白）就是人工判断（`isManualDecide`） | `金额大于 5000` |
| `config` | `Cfg` | 否 | 类型自己的配置项，key 见 `SPEC-sop-11` 各类型的配置项表；值一律是字符串 | `{ model: '', output: 'result' }` |

`SopCase`：`{ key: string; label: string }`。`key` 在节点内唯一（默认 `yes` / `no`、`c1` / `c2`，新加的为 `c<时间戳36进制>`），`label` 是显示名，保存时不能为空。

`Json`：`Record<string, unknown>`，步骤的输入输出、执行参数都是它。

`SopRun`（`web-next/src/sopflow.ts`）：一次执行。

| 字段 | 类型 | 必填 | 说明 | 取值 / 示例 |

| `sop_id` | `string` | 是 | 来自哪个流程；流程删了也留着 | `sop_feedback` |
| `sop` | `Sop` | 是 | 开始执行时的流程定义快照；之后改了流程，进行中的执行仍按原来的步骤走完 | |
| `title` | `string` | 是 | `流程名 · 第一个输入值的第一行（按换行或 \| 切，前 16 个字）` | `客户反馈转需求 · 梁晚晴` |
| `step_through` | `boolean` | 是 | 逐步确认：每一步执行前停下来等人确认输入；执行中可切换 | `false` |
| `stopped` | `boolean` | 是 | 被终止 | `false` |
| `started_at` | `number` | 是 | 开始时间，毫秒时间戳 | |

| `steps` | `RunStep[]` | 是 | 每个步骤一条，顺序和 `sop.steps` 一致 | |

`RunStep`（`web-next/src/sopflow.ts`）：一次执行里一个步骤的记录。

| 字段 | 类型 | 必填 | 说明 | 取值 / 示例 |
|---|---|---|---|---|

### 执行语义

正式产品的执行引擎（SOP-01b）按这里的语义实现，原型 `sopflow.ts` 的 `startRun`、`advance`、`tick`、`act` 是参照。

1. **放行**：一个 `pending` 步骤的依赖全部结束（`done`、`skipped`、`bypassed`）时放出。依赖同一步的几步同时放出，就是并行；依赖多于一步的，等几路都结束才放，就是汇合。一轮放出的步骤可能让下一轮又能放，循环到不动为止。
2. **分支**：步骤有 `branch` 且判断步骤选的不是这个分支，或者它的依赖全是 `bypassed`，标 `bypassed`（日志「所在分支未被选中，不执行」），不执行。
3. **输入**：见 `RunStep.input`。汇合时按上游 key 分组，免得字段互相覆盖。
4. **逐步确认**：`step_through` 为真时，放出的步骤先停在 `paused`（日志「执行前暂停，等待确认输入」），确认后才开始计时。
5. **出结果**：`running` 到 `ms` 后：先判失败（步骤自己的 `fail`，再判类型的 `fail`），失败转 `failed`；分支节点（不是人工判断）算出 `route`，转 `done`（日志「判断结果：走「分支名」，原因」）；人工判断转 `review`（「等待人工判断走哪个分支」）；人工检查转 `review`（「已就绪，等待人工检查」）；其余转 `done`（「完成，用时 N.Ns」）。
6. **判断规则**：示例流程用写死的 `decide`；分类器用类型的 `route`；条件分支有 `rule` 时原型不求值，走第一个分支，原因「按规则「…」判断（原型模拟）」。
7. **结束**：全部步骤结束时写 `ended_at`。被终止的执行不再推进。
8. **快照**：执行带开始时的流程定义，之后改流程不影响它。删除流程后执行记录保留，`sop.name` 照常显示。
9. **失败记运行异常**：步骤每次失败（按「执行 + 步骤 + 次数」只记一次）记一条运行异常，指纹 `sop:<流程 id>:<步骤 key>`，模块 `SOP`，标题「「流程名」步骤名失败」，上下文带 SOP、步骤、执行、输入（见 `SPEC-settings-18`）。演示数据里那次失败不重复记。因为模型服务商不可用失败的不按步骤记，按服务商记成一条（见 9a）。
9a. **等服务商恢复**（TSK-0392，正式产品，原型只做展示）：AI 处理、参数提取、问题分类器、迭代这四种经模型补全的步骤，失败原因是服务商不可用（服务商熔断中，或自动重试用完仍是 5xx / 连不上，`SPEC-settings-7.23`）时：IM 消息、定时、插件、子流程发起的执行不标失败，步骤仍是 `running`，带 `provider_wait`（服务商、最近一次失败、开始等的时间、下次重跑时间），不占调模型的名额；到服务商给的探测时间（没熔断时 1 分钟后）、或同一服务商有别的挂起步骤重跑成功时，原地重跑这一步（同一条执行，不新建执行，所以同一条 IM 消息不会重复建任务；IM 触发本身也按消息去重）。最多等到执行发起后 24 小时，过了照常失败，错误后面加「（执行发起后已等了 24 小时，服务商仍没恢复，不再自动重跑；修好后在这里点重试）」。手动、Agent 发起的执行有人在看，直接失败。日志：第一次挂起记「服务商「名称」不可用（原因），先挂起，等它恢复后自动重跑这一步；HH:MM:SS 先探测一次，最多等到执行发起后 24 小时」，重跑成功记「服务商「名称」恢复了，重跑这一步」，中间被挡下不再记。运行异常不分流程、步骤，按服务商记一条：指纹 `sop:provider:<服务商 id>`，模块 `SOP`，标题「服务商「名称」不可用，影响 N 次执行」（N 是正在等这个服务商的执行数，失败的另加 1），正文写原因、熔断和探测时间、这一步怎么处理了、怎么修（去 设置 → 模型服务商 检查 base_url，或设「失败时改用」，或在节点里换服务商）；每条执行第一次挂起时记一次。挂起状态在内存，服务重启后执行中的步骤照常重跑一次，还不通就重新挂起。
10. **Claude Code 执行**（AUTO-01，`claude_code`）：放出后按配置渲染工作目录、提示词、关联任务，交给本机 Claude Code（内核 `Runs().StartClaudeCode`，带角色、超时，要求结束前用 `pmw_finish_run` 回报 `summary` 和结构化 `result`）；配了关联任务时在任务上留一条执行记录（任务抽屉「执行记录」里能看到、能取消，执行 id 就是那条记录的 id）。发起后步骤停在 `running`，记下 `claude`，收到 `run.finished`（兜底每 5 秒查一次）后出结果：成功时输出 = 输入加 `status`、`summary`（回报的摘要，没回报取过程记录末尾）、`result`（回报的结构化结论，没回报为 `null`）、`run_id`，下游条件分支能直接判断 `result.verdict`；执行失败、被取消、超时（配置的超时到点由执行器取消，再过 1 分钟没收尾由 SOP 取消）这一步失败，可重试（重新发起一次）。终止执行、退回、重试时取消在跑的那次。服务重启后那次执行的结果拿不到，这一步失败，提示重试会重新执行。被条件回退退回重做时（输入里有 `feedback`、提示词模板没引用它），提示词后面自动附「上一轮被退回（这是第 N 轮）」一节：原因、上一轮的意见、结构化意见。
10a. **执行任务**（TSK-0411，`task_run`）：和 `claude_code` 共用发起、等待、Claude Code 名额和需求预算（第 10 条、`SPEC-sop-15`），区别：工作目录不配，按任务自己的工作目录 → 所属项目的工作目录继承（同任务页「执行」）；任务和项目都没设、目录不存在或不可写时不发起，失败原因写明任务编号、继承自哪里（「任务 TSK-0001 没有工作目录：任务自己没设，所属项目「X」也没设；在任务或项目上设好工作目录再执行」「任务 TSK-0001 的工作目录（继承自所属项目「X」）不能用：工作区目录不可写…」）；提示词由任务拼（编号、标题、所属项目、工作目录、验收标准，要 Claude Code 先用 `pmw_get_object` 读任务全文，配置的「附加要求」拼在后面）；一律可写，执行记录留在任务上。`on_fail` 为 `continue` 时没有工作目录、发起失败、执行失败都不让这一步失败：步骤完成，输出 = 输入加 `status: 'failed'`、`error`（原因）、`summary: ''`（执行失败时另有 `run_id`），下游用条件分支判断 `status 等于 done` 回报；不记运行异常。
10b. **更新任务**（TSK-0411，`task_update`）：按写节点的口径（第 9 条以外同 SOP-02a 写节点：操作者 `sop#<执行 id>`，记审计，重启重跑同一次尝试不重复改）改已有任务的负责人、状态，经内核 `ObjectWriter.UpdateTask`；都没配时只读取。负责人认联系人 id 或名字（去掉 @ 和引号），名册里没有时不改、不失败，输出 `task.assign_ok = 'no'`、`task.assign_note = '没找到「X」，任务留着没分配'`；状态是任务类型的状态 key，不认时失败「改任务 TSK-0001 失败：…」。输出在输入上加 `task: { id, ref, title, status, owner_id, assignee, project_id, project, workdir（继承后的有效目录）, assign_ok, assign_note, changed }`。
11. **条件回退**（AUTO-02，`loopback`）：出结果时按回退条件求值（写法同条件分支）。不成立走「通过」`pass`。成立且已退回次数 `loops` 小于 `max_rounds`：`loops + 1`，目标步骤（`target`，必须是上游）下游的所有步骤（含本步）回到 `pending`、清掉输出，记 `round`；目标步骤重新执行（逐步确认时先 `paused`），`attempts + 1`，输入 = 它按依赖算的输入加 `feedback`（本步的输入，另加 `round` 第几轮、`reason` 原因、`from` 本步 key；不往下嵌套上一轮的 feedback），记 `round`、`rework_reason`。日志：本步「条件「…」成立，退回「目标」重做（第 N 轮，最多退回 M 轮）」，目标「第 N 轮：被「本步」条件「…」成立退回重做」，中间的步骤「上游「目标」被退回重做，这一步重新等待」。成立且已退回 `max_rounds` 次：走「超限」`over`，原因「已经自动退回 M 轮，条件「…」成立，超过上限」；没有步骤接在「超限」上时这一步失败（原因同上，加「；没有步骤接在「超限」出口上」）。回退目标写在配置里不是依赖，校验依赖无环时不算。

### 数据

最近 500 条加没走完的（TSK-0486）：原型的执行全在内存里，没有条数上限。正式前端的执行列表取两份再按 id 合并：最近 500 条（`GET /api/sop/runs?limit=500`，接口上限）和「没走完、待我处理」的（`GET /api/sop/runs?status=running,waiting,failed&limit=500`，后端的 `status=failed` 不含已重跑的），两边都有的取最近那份。原因：执行一多（11-06 生产 2128 条），最近 500 条可能全是已完成的，较早的失败、等人、执行中的执行就看不见，待我处理会空着而今日有条目。合并后的这份给执行记录、待我处理、流程库统计、流程详情共用，所以执行记录「执行中」「待我处理」「失败」分段的条数不论多早都算全；「全部」「已完成」只算最近 500 条加没走完的（列表本身就只取到这些）。正式前端 `core/data/sop.ts` 的 `useSopOpenRuns`（缓存键 `['sop', 'runs', 'open']`，在 runs 前缀下，事件和重跑的缓存更新照样作用），合并在 `plugins/sop/model.ts` 的 `mergeRuns`、`Page.tsx`。

批量重跑（`SPEC-sop-4.13` 到 `4.19`）：原型在 `sopflow.ts` 的 `rerunRuns`（`RerunAction`、`RerunResult`、`RERUN_MAX`），「流程发起后改过」用 `flowChanged` 比快照和现在的步骤、字段；界面在 `sop.tsx` 的 `RunList`、`RerunDialog`，接线在 `App.tsx`。正式产品 `POST /api/sop/runs/batch-actions`，body `{run_ids, action: retry | relaunch}`，`run_ids` 1 到 200 条，回 `{done: [{run_id, new_run_id?, steps?}], skipped: [{run_id, reason, new_run_id?}], failed: [{run_id, error}]}`（后端 `internal/plugins/sop/runbatch.go`）；重新发起的执行 `source` 为 `manual`、`source_ref` 为被重新发起的（顶层）执行 id、`source_name` 为「批量重跑」；「流程发起后改过」比执行的 `flow_version` 和流程现在的 `version`。正式前端在 `plugins/sop/RunList.tsx`、`RerunDialog.tsx`、`rerun.ts`，接口在 `core/data/sopBatch.ts` 的 `useRerunSopRuns`，成功后先按结果改缓存里的执行列表（`applyRerun`：重新发起的记 `relaunched_to`、重试的改执行中），再报 `sop-run` 刷新列表。

### 每种节点的配置项

下表「执行（原型）」是 `run` / `fail` / `route` 的模拟规则；正式产品怎么真做见 `SPEC-sop-12`。耗时是原型 `ms`。

调模型的四种节点（`ai`、`extract`、`classifier`、`iterate`）都有「Agent」配置项（`agent`，值是 Agent id）：选了就用这个 Agent 的服务商、模型、思考档位（`SPEC-settings-9.44`），它的指令拼在节点自己的系统提示前面；`ai` 节点上的服务商、模型这时不显示，执行时也不看。不选时按「设置 / Agent」里「其他后台调用」的场景默认 Agent（`SPEC-settings-8.14`），那里也没选就照老样子：`ai` 用节点选的服务商和模型（都没选用默认服务商），其余三种用默认服务商，思考按模型默认。节点上不单独配思考，要快就给节点选一个思考关掉的 Agent（比如「内容分诊」）。画布摘要：选了 Agent 写 Agent 名。

| 配置项 | key | 控件 | 必填 | 默认 | 选项 / 占位 / 提示 |

日期占位：`{{date}}` 本机时区 `YYYY-MM-DD`，`{{month}}` `YYYY-MM`，`{{time}}` `HH:MM`（文件路径里写成 `HHMM`）；输入里有同名字段时以输入为准。

正式产品（`SPEC-sop-12.35`）：
- 只写进这个项目 `props.related` 里列的目录之一（关联目录存成 `file://` 也认），关联目录本身不存在时失败，不替用户建；目录下缺的中间目录自动建。

- 文件已有：前面补到空一行再追加；内容末尾补换行。单次内容最多 64 KB，要是 UTF-8。
- 要 SOP 插件的 `fs:write:project` 权限，没确认时失败「插件 sop 的 fs:write:project 权限还没确认，到插件管理里升级并确认」。
- 幂等同写节点：服务重启后重跑同一次尝试时不重复追加；每次写入记一条审计（`append` / `file`）。
- 输出加 `file: { path, rel, dir, dir_label, project: { id, ref, name }, bytes, created }`，`path` 是实际写入的绝对路径。

## SPEC-sop-14 执行并发（设置 > SOP 编排）

IM 触发的流程一来消息就发起一次执行，Slack 一次同步几十条消息时几十条执行同时调模型，本机推理跟不上。

原型在 `web-next/src/sop.tsx` 的 `SopSettingsPage` 和 `sopflow.ts` 的 `gateRuns`，设置分项是 `settings.tsx` 的 `sop`。

## SPEC-sop-15 流水线治理（设置 > SOP 编排）

### 数据

阶段变化：原型 `Task.stage_log`（`tasks.md` `SPEC-tasks-11`「阶段变化历史」）；正式产品取审计 `GET /api/audits?target_type=object&target_id=<任务 id>&kind=stage`。SOP 部分正式产品走 `GET /api/sop/pipeline/{id}`（`{task_id, runs, claude, budget, blockers}`，执行按开始时间早的在前，每步带状态、尝试次数、轮次、退回次数、`hold`、排队；`claude` 是这条需求的 Claude Code 账本；`blockers` 是等人的步骤，形状同 `GET /api/sop/waiting` 的一条）。接口见 `docs/api-contract.md`「SOP 编排插件 sop」。
