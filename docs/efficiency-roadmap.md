# 提效功能规划：产品经理 / 项目经理 + 多 Agent 承接执行

规划日期：2026-09-15 · 目标读者：本项目决策与实施
前置约束：本文不包含安全与权限类功能（用户明确后置）。凡涉及写权限的设计，只保留"数据可信度"必需的最小部分。

---

## 一、目标拆解与当前差距

目标可拆成四个环节，现状是**前两环只有一次性、第三环是零次、第四环缺骨架**。

| 环节 | 目标 | 现状 | 差距性质 |
|---|---|---|---|
| 收集 | 人 + Agent 从多渠道持续收集 | 单渠道一次性导入（81 条，人工创建的 20 条已全删） | 渠道缺失 |
| 汇总 | 大量需求/待办的归集与去重 | 分类树 100% 在用、标签 98 条；无自动归类、无去重、无汇总节奏 | 自动化缺失 |
| 跟踪 | 到期、停滞、流转、提醒、度量 | 字段与界面已备好；到期 1/81、负责人 11/81、`task_runs` 0 | **机制缺失：无人催** |
| 执行 | 调用不同 Agent 同步完成工作任务 | 单对象、手动、阻塞式执行器（0 次使用）；MCP 只能读写数据，不能接活 | 骨架缺失 |

结论：提效的杠杆不在"再加功能面"，而在**把第三环从零次变成每天发生，把第四环从"Agent 能写数据"升级为"Agent 能接活"**。

---

## 二、关键判断：大部分规划是"补一层"，不是重构

这是本项目最有利的一点。已有资产与它们能直接支撑的新功能：

| 已具备 | 可直接支撑 | 增量成本 |
|---|---|---|
| `revisions` 字段级修订（135 条） | 度量看板：周期时间、状态停留时长、按时交付率、范围变更次数 | 低（纯 SQL + 图表） |
| `counts.stalled`（14 天口径已实现） | 停滞推送，只差调度器 + 通知通道 | 低 |
| `counts` 的 today/week/overdue | 今日聚焦页 | 低 |
| `links.duplicates` 关系 + 标签合并实现 | 相似需求召回与一键合并 | 中 |
| `shortcuts` 已能存 ViewDescriptor | Saved View 升为一等实体（侧栏独立区 + 快捷键） | 低 |
| `object_types` 自定义 + `dictionaries` 通用枚举 + `props` JSON | RAID / 里程碑 / 干系人全部零代码注册 | 低（以数据配置为主） |
| `task_runs` + `runner`（SSE、进程组取消、输出落库、1MB 截断） | 执行队列 + 并发上限 + 运行中心 | 中（骨架已有） |
| `agent_artifacts`（挂 session，相对路径） | 产出回流到对象：加 object_id + 抽屉展示 + 沉淀为 doc | 低 |
| `agent_providers` 多供应商接入层 | Agent 注册表（多 Agent 复用同一层） | 低 |
| MCP 9 工具（6 读 3 写） | 补批量 / 派发 / 运行状态 / 视图查询 | 中 |
| `workdir` 对象级继承（任务→项目） | 按项目隔离 Agent 产出目录，已就绪 | 无 |
| 8 种批量操作（并发 5、部分失败逐条报错） | 批量派发、按筛选全量执行 | 低 |

## 三、功能规划（按提效杠杆排序）

### Tier 1 — 找得到 + 每天有动作（不修补则规模上不去）

**1.1 检索语义修复**
- 现状：`Query` 是单一连续子串 `LIKE`。实测「权限 分权」「支付 Stripe」均 0 命中，而库中有匹配内容。
- 补：查询词按空格/标点拆分 → 多词 AND（默认）或 OR；命中高亮；检索范围可选（标题/正文/标签/编号）。
- 可选后置：中文分词、FTS5 trigram。
- 要点：先做拆分 + AND，这一步就能解决当前 100% 的失效场景，且不动索引结构。
- 验收：搜「权限 分权」命中 REQ-0045。

**1.2 Saved View 升为一等实体**
- 现状：`shortcuts` 已能存视图描述符，但列表工具栏的「另存为视图」是禁用按钮（标注 M2）。
- 补：`views` 表（名称/描述/查询条件/排序/分组/视图类型）；侧栏独立「保存的视图」区（线框稿已设计）；快捷键直达；CRUD 接口。
- 价值：大量待办下，日常视图切换从"点 6 次筛选"变成"按一个键"。

**1.3 今日聚焦页**
- 现状：`counts` 五档口径齐全，但没有承载它的落地页。
- 补：打开即见的五段——今日到期 / 逾期 / 我负责 / 停滞且我负责 / 本周将到期；每段支持一键动作：排今日计划（设 doing + 排期）、顺延、催办、派发给 Agent。
- 价值：从"面对 81 条自己筛"变成"每天有明确动作清单"。

**1.4 调度器 + 主动推送**
- 现状：无调度器；顶栏通知按钮只有角标、无点击行为。
- 补：内置 cron + 可配置任务（每日扫逾期与停滞、每周变更摘要、Inbox 积压检查、自动快照）；推送通道：桌面通知、IM（飞书/Slack webhook）、Markdown 摘要可转发；每次运行落运行日志、可重试。
- 价值：**这是把跟踪从零次变成每天发生的关键，也是全表最高杠杆的一项。**

**1.5 批量按筛选全量执行**
- 现状：批量动作作用于"已加载的 50 条"，全选受加载量限制。
- 补：「当前筛选下全部 N 条」的明确语义；批量按规则赋值（如按分类套默认负责人）；批量派发给 Agent；导出当前筛选为 CSV/Markdown。
- 价值：大量数据处理从"翻页点选"变成"一次下单"。

**1.6 度量看板**
- 现状：`revisions` 数据完整，未被消费。
- 补：周期时间（created→completed）、各状态停留时长、按时交付率、每周新增/关闭/范围变更次数、按负责人负载。
- 价值：成本极低，且是验证"跟踪是否真的在发生"的仪表。

### Tier 2 — Agent 能接活（用户明确诉求：调用不同 Agent 同步实现工作任务）

这一层是新增环节，目标是把 Agent 从"会写数据的聊天对象"变成"能承接工作、并行执行、产出归位的工作单元"。

**2.1 Agent 注册与能力声明**
- 现状：只有 `agent_providers`（模型接入点），没有"Agent 是谁、能干什么"。
- 补：`agents` 表——名称、用途描述、可承接的对象类型/标签、执行方式（内置对话 / 本机 CLI / 外部 MCP / HTTP）、默认工作区、并发上限。
- 价值：派发时系统知道"这件事归谁"，而不是只有一个默认模型。

**2.2 任务模板库（Skill / 提示词）**
- 补：`task_templates`——名称、适用类型、提示词正文（支持 `{{title}}` `{{body}}` `{{ref}}` 等变量）、预期产出（写文件 / 改字段 / 出报告）、可绑定到对象类型或视图。
- 首批建议模板：需求结构化、写 PRD、竞品调研、周报汇总、会议纪要抽待办、需求去重判定、风险识别。
- 价值：把"调用不同 Agent 干活"变成一键动作。这是本诉求最直接的提效形态。

**2.3 派发机制**
- 现状：`POST /api/objects/{id}/run` 只能单对象、手动、阻塞。
- 补：`agent_tasks` 表（对象、模板、指定 Agent、状态、优先级、依赖）；三个派发入口——详情抽屉一键派、列表批量派、按规则自动派（如"status=planned 且 owner=我 的需求 → PRD Agent"）。
- 价值：人从"逐个打开执行"变成"批量下单"。

**2.4 执行队列 + 运行中心**
- 现状：runner 单次执行、无并发控制、SSE 单连接。
- 补：执行队列、全局与单 Agent 并发上限、失败重试、断点续跑；运行中心页（排队中/执行中/失败/已完成，含进度、耗时、Agent、关联对象）；执行流需支持全局事件通道（SSE 单连接不够用）。
- 价值：**这是"同步实现工作任务"的落点——多个 Agent 并行跑，人看一个面板。**

**2.5 产出回流**
- 现状：`agent_artifacts` 只挂 session；产出散在 workdir 里没人看。
- 补：artifacts 增加 object_id；详情抽屉新增"产出"区（预览/下载/在 Finder 打开）；一键把产出沉淀为 doc 对象并自动建 references 关联；正文级产出可写回对象 body（带草稿标记）。
- 价值：Agent 干完活，结论落在对象上而不是文件系统里。

**2.6 运行记录与成本**
- 补：`agent_run` / `agent_step` / `tool_call`；token、耗时、成本（按供应商单价）、成功率；按对象 / Agent / 模板 / 时间维度汇总。
- 价值：知道钱花在哪、哪个模板值得留、哪个 Agent 靠谱。

**2.7 人在环（轻量版）**
- 说明：这不是权限，而是**数据可信度**——避免 Agent 改坏主表后人工返工，属于提效。
- 补：Agent 对主表的写操作落"建议"状态，详情抽屉显示"Agent 建议的变更"并一键接受/拒绝。
- 范围建议：只拦「状态 / 负责人 / 正文」三类，产出文件不拦。

**2.8 周期任务（例行工作自动生成）**
- 补：规则表（rrule 或简化表达 + 模板对象），到期自动生成对象并派发给指定 Agent。
- 适用：周报、例会跟进、月度复盘、定期巡检。
- 价值：例行工作从"靠记忆重建"变成"自动出现"。

**2.9 MCP 工具补齐**
- 补：批量创建 / 批量更新、派发任务给指定 Agent、查询运行状态与产出、按 Saved View 查询、聚合统计（度量口径）。
- 价值：外部 Agent（Claude Code / WorkBuddy 等）能读到平台判断并承接工作——这是"多渠道 + 多 Agent"的接口面。

### Tier 3 — 规模化质量

**3.1 需求去重与合并**
- 现状：`links.duplicates` 关系已定义（全库仅 1 条）、标签合并已实现，需求没有合并。
- 补：相似需求召回（先用标题/关键词相似度，后可上向量）；候选列表 + 一键合并（保留主对象、合并正文、迁移关联/标签/产出、被并对象标记并保留反向链接）。
- 价值：需求池越大重复越多，这是纯人工成本项。

**3.2 导入器（当前真实用法的正规化）**
- 现状：无正式导入功能，81 条是经 MCP 塞进去的。
- 补：CSV / Excel / Confluence 导出导入；字段映射界面；导入预览；按标题相似度与来源 ID 去重；按 `batch_id` 可整体回滚。
- 价值：直接消除人工搬运与重复录入。

**3.3 Inbox 分流工作流**
- 现状：有 Inbox 状态与 4 条数据，无分流动线。
- 补：Inbox 逐条/批量处理视图（分派类型 + 分类 + 负责人 + 到期），键盘流优先。
- 价值：收集进来的东西当天能归位，而不是沉在 Inbox。

**3.4 列表规模适配**
- 补：虚拟滚动或游标分页；列表内快速内联编辑；列自定义与列顺序持久化。
- 触发条件：数据量到千条量级时再做（当前 81 条无感）。

### Tier 4 — 双角色深化（按提效排序）

**产品经理侧**
- 优先级排序模型（RICE 或自定义权重），支持拖拽排序并持久化
- 需求评审流转（评审状态、评审人、意见）
- 需求 ↔ PRD ↔ 技术方案双向绑定；「未被任何文档覆盖的需求」视图
- 需求变更历史视图（单对象已有活动 Tab，缺"范围内全部变更"）

**项目经理侧（按提效优先级）**
- **容量与负载**：按人看在手任务数、工作量、超载预警 —— 提效最直接，且只需聚合 `objects.owner` + 未完成任务
- **RAID 四台账**：风险 / 假设 / 问题 / 依赖。注册 4 个 object_type + 字典（概率、影响分级）即可，零代码；风险值 = 概率 × 影响；复审日期提醒复用调度器
- **里程碑 / Release / Sprint 层级**：注册 object_type + parent 关联
- **验收管理**：AC 清单、UAT 记录、缺陷关联
- **变更控制**：需求基线冻结、变更申请、影响分析（列出受影响的未完成任务与文档）
- **干系人**：person 类型 + 角色/影响力/沟通记录
- **会议闭环**：议题收集 → 纪要 → 待办抽取（Agent 模板）→ 决议进 ADR

### Tier 5 — 收集渠道接入（让收集持续发生）

- **IM 转发入库**（最高优先）：飞书 / Slack 消息一键转需求或待办，落 Inbox 并带来源链接与原消息
- 会议纪要 → 待办抽取（可复用 2.2 模板能力）
- URL 抓取正文（存 resource + 摘要）
- 邮件转需求
- 系统级快速捕获（macOS 全局快捷键 / 菜单栏 / 分享菜单）
- 剪贴板与浏览器插件

## 四、建议实施顺序

以"最短路径让跟踪开始发生 + Agent 能接活"为原则：

1. 检索语义修复（1.1）—— 解决当前唯一影响日常使用的缺陷
2. 调度器 + 主动推送（1.4）+ 今日聚焦页（1.3）—— **让跟踪从零次变每天**
3. Saved View（1.2）+ 批量按筛选全量（1.5）—— 规模化的操作效率
4. Agent 注册（2.1）+ 模板库（2.2）+ 派发（2.3）—— **让 Agent 能接活**
5. 执行队列 + 运行中心（2.4）+ 产出回流（2.5）—— **让多 Agent 并行可管**
6. 人在环轻量版（2.7）+ 运行成本（2.6）
7. MCP 工具补齐（2.9）+ 导入器（3.2）—— 打开外部 Agent 与外部渠道
8. 去重合并（3.1）+ 度量看板（1.6）
9. 双角色深化（Tier 4），每批上完先观察是否被真实使用，再决定下一批
10. 收集渠道（Tier 5）

关键原则：**每完成一批，先看数据是否被使用，再决定下一批。** 当前 81 条数据已经证明"建好界面不等于发生行为"，避免继续堆空转的功能面。

## 五、需先拍板的三件事

这三项影响实现方案，建议先定：

**1. Agent 在哪里执行**
- 方案 A：平台内置（自建队列 + 内置模型调用）
- 方案 B：平台只管派发与协调，执行交给外部（本机 Claude Code、任意 MCP 客户端）
- 方案 C：两者都支持，执行器做成可插拔接口
- 建议：**C**。依据是实测——内置 Agent 只跑过一次「hi」、执行器 0 次调用，而外部 Claude Code + MCP 是真实使用路径。`runner` 抽成 interface 的成本不高，但决定 2.4/2.5 的形态。

**2. "大量"的量级**
- 千条 / 万条 / 十万条，决定检索方案（拆分 + AND 是否够，是否必须上 FTS5 或向量）与列表分页策略。
- 建议：先按千条设计（当前 81 条），把检索做成可替换实现。

**3. 现在是否预留多工作区与 `owner_id`**
- 安全权限虽然后置，但 `objects` 表目前只有 `owner TEXT`，没有 `owner_id`。现在预留成本很低，事后补是重构。
- 建议：**现在就在数据层预留**（加列 + 默认值），功能层先不做权限。

## 六、明确不做

- 安全与权限体系（用户后置）
- `specs` / `spec_versions` 基线治理四张表：其设计目的是解决"Agent 读到废弃方案"，当前库里还没有多版本方案。等方案库真出现多版本再建
- 关联图可视化、日历视图、时间线视图：等跟踪闭环跑起来、数据侧证明需要再做
- 深色/浅色之外的主题定制、移动端原生 App
