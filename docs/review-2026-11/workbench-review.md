## 0. 结论先说

**这是一个「框架接近一流、产品还在二流」的工作台。差距不在能力，在收口。**

- 架构上它已经不是自建脚本，而是一个真正的插件化平台：9 个第一方插件、13 个后端扩展点（12 个有真实消费方）、17 个前端扩展点（12 个接线）、清单/迁移/权限/停用撤注册这套生命周期是闭环的、有测试的。这在同类个人工具里是罕见的资产。
- 但产品上它没有回答「我是谁」：README 说「产品经理的个人工作台」，代码里有 6 个角色工作台（PM / 研发 / 运营 / 视频 / 交易 / 全部），数据里每天真正发生的是「Claude Code 改任务 + IM 收消息 + 少量私聊回复」。三个身份叠加，导致功能面按「能力」生长，而不是按「每天要做的一件事」生长。
- 好用层面，最核心的承诺「一个入口看今天」目前不成立：今日页汇总出 **910 条待处理 IM**（其中 848 条是 10-30 一次性回填的历史私聊，发送时间跨 2025-04～2026-10，从未分诊）；`notifications` **289 条、283 条未读**——其中 267 条 review 通知对应的任务 **266 个已经是 done**，283 条未读全部积压在 10-28～11-06（之后 3 天没有新通知），且没有列表入口；全库 **到期 0/502、负责人 245/468（243 个是「Claude Code」，人类只有 2）**。工具造好了，注意力的入口和生命周期都没造好。
- 扩展层面，机制是真的，但「模块化复用」欠了三笔大账：**跨插件实体关联原语**（`project_id` 散落在 18 张表）、**通用设置/文件/进程句柄**（5 个插件各造一套设置，8 个文件裸 import `database/sql`）、**页面级 UI 骨架**（23 个基础组件撑 548 个页面文件，11 份 `timeAgo`、19 种表 CSS）。每加一个功能，都在复制一套结构。
- 减法空间同样明确：**交易 + 视频两个插件占插件后端代码的 42%（32.2k 行），数据侧是 0 笔交易、1 个空视频**；再叠加 **47k 行未冻结的原型 + 12k 行旧前端**。这三块是下一版最确定的收益。

如果只记一句：**别做第 13 个模块，先把「今天该做什么」这一个功能做对。**

## 1. 先校准：它现在实际是什么产品

| 视角 | 说什么 | 证据 |
|---|---|---|
| 文档说 | 产品经理的个人工作台：需求、任务、项目、文档、IM、联系人一处，任务交给 Claude Code，SOP 串自动流程 | `README.md:1`；`README.md` 宣传 14 个模块 |
| 代码说 | 内核 + 插件 + 多角色工作台平台：6 个 workspace 模板（PM/研发/运营/视频/交易/全部），菜单按角色组装，数据不隔离 | `workspaces` 表 6 条；`internal/workspace/store.go:1-3`；`docs/plugin-api.md` §6 |
| 数据说 | 一个「AI 研发流水线 + IM 收件箱」的控制台：写库主渠道是 Agent（`revisions.agent` 3098/4387 = 70.6%），MCP 回写产物 275 条，SOP 3,861 次执行里 55% 是已删除的旧流程、30% 是「忽略机器人消息」规则 | `usage-and-product.md` §1-2 |

**判断（推断）**：产品实际的身份是「个人 Agent 工作流控制台」，而文档身份是「PM 工作台」。这不是命名问题，它决定了三件事的取舍：菜单该默认放什么、数据模型该以什么为中心、哪些插件不该进默认包。

**为什么会偏**：这个工作台被用来开发它自己（提交历史全是 `TSK-xxxx`，SOP 里内置研发 pipeline，任务执行器接 Claude Code / DeepSeek）。**做「给开发/AI 用的功能」比「用工作台做 PM」更容易被验证、正反馈更快**，于是功能朝开发侧聚集（SOP 3,861 次、Agent 修订 3,098 条），而 PM 侧最该闭环的「收集→分诊→跟踪」反而没形成习惯。这是自举产品的典型偏置，不是执行力问题。

**必须选的定位**（三选一，影响后面所有建议）：

- **A 个人 OS / 多角色工作台平台**：保留 6 个 workspace，补数据隔离/上下文切换；代价是产品面继续变宽，每个垂直模块都要真用。
- **B Agent 工作流控制台**（建议）：核心是「任务/IM 进 → Agent 执行 → 产物/回执出」；视频、交易、ETF、浏览器降为可选包或拆走；PM 只是其中一个角色模板。
- **C 纯 PM 工作台**：砍掉执行器的大半、SOP 研发 pipeline、视频/交易；但现有代码和数据表明这不是用户实际在用的形态。

下文按 **B** 给建议；若选 A/C，第 5 节的「减法」清单需要相应调整。

## 2. 做得怎么样：评分与真资产

### 2.1 评分（以「好用且好扩展的个人产品」为标准）

| 维度 | 分 | 判据 |
|---|---|---|
| 架构与扩展机制 | **8.5/10** | 插件宿主闭环、13 个后端扩展点 12 个有消费方、权限分级、SOP 节点协议、前端清单双端同源 |
| 工程质量 | **8/10** | 36.5% Go 测试、251 个前端测试文件/1,844 用例、契约防呆、迁移校验和；扣分在无 CI、2 个时序 flaky、lint 红 |

| 日常可用性（注意力闭环） | **5.5/10** | 功能都可用，但今日/通知/跟踪三处不闭环（910 条待处理、283 条未读通知全部停在 11-06 前、到期 0） |
| 复用与一致性 | **5/10** | 后端 9 份 HTTP 信封/5 套设置/4 套等待；前端 7 类页面模式各手写 5–19 份 |
| 可持续性（维护成本） | **5.5/10** | 3 套前端、55 份文档 28.4k 行、155 张表、每次功能都要双写原型 |
| **总评** | **≈6.8/10** | 框架一流、产品二流；差距集中在「收口」而非「能力」 |

### 2.2 五个真资产（重构时不要丢）

1. **插件宿主是一套真框架，不是脚本拼装**：清单 schema 前后端同规则（样例/错误文案逐字一致）、迁移校验和（改过的迁移直接拒绝启动）、表前缀隔离、安装前备份、权限逐项确认、单独授权（`trade:live` 需用户本人 + 插件同意 + 二次确认 + 审计）、停用撤路由/撤订阅/停 Job（`internal/plugin/registry.go`，81 个宿主测试）。
2. **「执行器」抽象做对了**：`claude` / `deepseek(dsh)` / `agent` 三种 harness 共用任务单、事件、MCP 回写、产物登记、取消、历史（`internal/runner/harness.go`、`docs/deepseek-harness.md`）。这是「Agent 能接活」的正确形状，比多数 agent 工具的聊天框强。
3. **跨插件 SOP 节点协议是全仓最漂亮的协作设计**：`Spec.Params/Outputs/Effect/DryRun` + 挂起/唤醒 + 提供方停用时降级，三个插件共 31 个节点，调试按 Effect 模拟执行（`internal/plugin/sopnode.go`）。
4. **数据层与契约防呆**：前端 `core/data` 统一 hook/键/失效/错误，`invalidate.test.ts` 525 行；后端路由表 ↔ API 文档双向守卫 + `domain→api→store` 反射测试。长期工具最致命的「悄悄算错」被防住了。
5. **规格工程真的在驱动开发**：原型 → 19 份 SPEC（12,906 行）→ 编号任务 → 验收；10 月底 34 条走查拆成 20 个任务，本次复核抽查的 A/B 系列 21 项**代码层全部已修且有测试**。这个闭环质量很高。

## 3. 好用吗：核心承诺还没兑现

### 3.1 「一个入口看今天」被 910 条待分诊消息压垮

`todayNeeds` 的口径是「与我相关（@我 / @所有人 / 私聊）且 pending」（`frontend/src/plugins/im/index.ts:10`）。按这个口径，库里是：

- `im_messages` 3,462 条，`pending` 1,209；其中**与我相关 910 条**（私聊 848 + @我 57 + @所有人 5），未读 474。
- 848 条私聊全部来自 10-30 一次历史回填（`received_at` 同一天），**发送时间跨 2025-04-15～2026-10-26**（2025 年 149 条、2026 年 699 条），从未分诊。
- 今日页每组只露 3 条（`modules/today/model.ts:7 NEED_SHOW`），但**组头数字是 910**。

也就是说：打开「今日」，第一眼看到的是「IM 消息 910」。这不是「今天要处理的事」，是「一次没做过的历史分诊」。**一个注意力产品，最核心的数字失真，就等于没有首页。**

### 3.2 三处断裂（都有数据证据）

| 断点 | 数据 | 后果 |
|---|---|---|
| **通知没有出口也没有生命周期** | `notifications` 289 条、未读 283；其中 267 条 `task.review_requested` 里 **266 条对应任务已 `done`**、1 条对象已不存在；283 条未读全部积压在 10-28～11-06，之后 3 天没有新通知；前端只消费 `schedule.remind`（`core/data/notifications.ts:1-2`），顶栏只有搜索 | 既没有列表入口，也不会随对象状态自动已读；「通知」退化成只增不减的日志 |
| **处理完不收敛** | `im_replies` 1,015 条（全带外部 ID，含历史回填；10 月起 429 条），但消息 `done` 仅 4 条；`im_task_acks` 0；SOP「IM 任务回执」只跑过 2 次 | 回复可以勾「并处理」（`MessageDrawer.tsx:119`），但默认不勾、数据上几乎没人勾，消息仍留在 1,209 条待处理里 |
| **跟踪空转** | 存活对象 502 条：到期 **0/502**；负责人 245/468 里 **243 是「Claude Code」**，人类仅 2；`schedules` 只有 3 条（14 次执行，3 次因服务没开而 missed 且不补跑） | 「今日/逾期/停滞」五档聚焦没有可驱动物；节拍只存在于运维侧（巡检 + 点餐提醒） |

9 月评审的判词是「库建好了，节拍没有」。两个月后，**节拍在运维侧有了一点，在跟踪侧还是没有**；同时新增了一个更隐蔽的问题——通知有表、有事件、有未读，但没有出口。

### 3.3 结构性原因：功能完成度 ≫ 流程完成度

- 20 个 PR 任务几乎都是「按模块各修一遍」，没有把重复模式升级成共享层（`frontend-arch.md` §6）。所以修复率很高，但每修一条就多一份手写模式。
- 同理，IM 转任务支路在 11-06 一次批量分诊里跑出 **277 个 run / 216 条任务，3 分钟内全部软删**；之后 11-07/08/09 每天 SOP 只剩 4/2/9 条，回复 0。**功能被验证过，流程没被用起来。**（11-09 上午生产实例仍在实时收消息、跑忽略流程，说明实例是活的。）
- 批量分诊没有「先出建议、再确认建任务、可撤销」的两段式——唯一一次规模化使用以回滚收场，这不是偶然，是产品缺少「可反悔」的设计。

### 3.4 三套前端 + 同一概念多种长相

- `frontend/` 正式（76.4k 行）· `web-next/` 原型兼规格（41.6k 行 + 12.9k 行 SPEC，10-29 后仍有 **61 个提交、5 个文件未提交**）· `web/` 旧前端（12.4k 行，Makefile 已标「下个版本删」）。**旧前端 + 原型 = 54k 行，约等于正式前端的 71%**；同一条 SOP 规则修复（TSK-0498）在原型 JS 引擎里出现了第三份实现。
- 同一个概念在不同插件里长相不同：打开任务的 3 种框、5 种筛选控件语言、批量操作 3 种位置/上限、11 份 `timeAgo`、4 种提示/报错（`frontend-arch.md` §6）。用户要重新学每个插件。

## 4. 好扩展吗：机制 8 分，落地 6 分

### 4.1 真做到的（不重复第 2.2 节）

- 新增一个**后端最小插件**只需要 5 个文件（插件本体 + 清单 + 迁移 + 测试），实测 ETF 首个提交 1,167 行。
- **清单 → 注册** 的校验在宿主集中做（`provides` 声明、id 前缀、路由前缀、事件命名空间、连接器冲突），不是各插件自觉。
- 非测试代码**零跨插件 import、零内核表裸 SQL**（`internal/plugin/store.go:182-218` 按前缀拒绝；实测结果干净）。
- `optional_depends` / 强依赖 / 环检测都有声明与校验；SOP 节点在提供方停用时降级。

### 4.2 七个真缺口（按修复收益排序）

| # | 缺口 | 证据 | 影响 |
|---|---|---|---|
| 1 | **没有通用「实体关联」原语** | `project_id` 出现在 18 张表；`conversation↔project` 两套表（`im_conversation_projects` 62 行 / `projects_conversations` 10 行，9 行重叠）；`message↔task` 两套；`object_origins` 建了 0 行没人用 | 每加一种「X 关联 Y」就新建表 + 接口 + UI；停用/删除时的级联语义各写各的 |
| 2 | **没有通用设置 / FS / Process / 搜索 / 对象类型句柄** | 5 个插件自建设置（6 表 10 端点）；8 个文件裸 `database/sql`；7 文件直接 `exec.Command`；文档承诺的 3 条后端禁令只落地 1 条的一小半（AST 测试只禁 `http.DefaultClient/Get/Post/PostForm/Head` 5 个符号） | 插件越大越像小内核；「权限靠代码路径自觉」 |
| 3 | **清单校验单向 + 装配手工** | 清单写了 `settings/search/agent_tools/object_types` 但代码零注册完全合法；新插件要手改 `cmd/pmw/main.go` + 两个契约测试（共 ≈8 处），**漏一处不报错、测试照绿**；无脚手架 | 静默漏注册是这类平台最常见的慢性病 |
| 4 | **`Core` 宽接口**：27 个方法全量下发，11 个只有 ≤1 个插件用（`Log/Store` 之外没有真正公共能力） | `internal/plugin/plugin.go:90`；browser 只用 3 个方法也拿到 27 个 | 第三方开放前必须拆能力组；测试替身成本高 |
| 5 | **生命周期非原子、停用是「尽力而为」** | 升级顺序 `migrate→写新版本→stop→collect`，`collect` 失败留「已升级未启动」且无回滚（文档说「状态表不动」，与实现不符）；停用超时后协程残留，**残留时仍可卸载**（先删表后协程写表）；无 deactivate 钩子，19 处裸 goroutine 不归宿主管 | 长期运行的平台，最难查的就是这类「半状态」 |
| 6 | **内核/插件边界划在「功能」上，不是「能力」上** | im / projects / sop 实为内核级（非测试 37.3k 行，占插件代码一半；`conversations`、身份、`project` 类型、SOP 调度都在内核）；trade 是 17.4k 行单体，违背 dev-plan「拆 4 个可独立安装插件」；`NetworkHosts` 把 im/video/trade 的 49 行域名写死在内核 | 「插件化」对第一方只兑现一半；**trade 停用了，但路由/表/代码每次构建都在** |
| 7 | **前端没有公开 API 面 + 页面层无复用** | 插件可 import 全部 21.5k 行 core（无 `core/public.ts`）；`core/data` 成跨插件总线（视频用 IM 的 hook、IM 用 SOP 的 hook）；`core/ui` 23 个组件撑 548 个生产文件；**oxlint 当前 3 个边界 error，且没有 CI** | 边界规则是资产，但当前是「未兑现的资产」 |

### 4.3 扩展成本量化

- **新插件**：后端最小约 8 个手工落点（5 文件 + main.go + 2 个契约测试清单），完整插件（含前端）几十上百文件、跨 8 个目录；**没有生成器/脚手架**。
- **新功能**：因为页面骨架没复用，一个「列表 + 筛选 + 抽屉」页面每个插件重写 100–200 行；因为关联原语缺失，一个新「X 关联 Y」要新增表 + 迁移 + 接口 + 前端选择器。
- **验证成本**：Go 全量测试 **51 秒**（2 个时序敏感用例在并行负载下会红，单独跑绿）；前端全量 vitest **39 秒**；但两边都**没有接进 `make check`/CI**，`make test` 只跑 Go。

### 5.2 非功能类「不必要」

- **旧前端 `web/`**：12.4k 行 + 3.7k CSS、50 文件、独立 `node_modules`；`make build` 默认早就不嵌它。**删**（1–2 小时）。
- **原型 `web-next/` 的持续双写**：41.6k 行代码 + 39MB 截图，10-29 后 61 个提交、5 个文件未提交；同一业务语义已有 Go 生产 + 原型 JS 引擎两份实现。**打 tag 冻结，规格降级为 md + 截图基线**（0.5–1 天），不要把「原型即规格」无限期执行下去。
- **文档对象 / 资源 / 笔记三个对象类型**：`doc/resource/note` 对象各 0 条（文档模块实际用的是挂载本机目录）。收敛为「目录挂载」一种知识载体，别再养三套状态机。
- **知识库**：2 个库、0 文档、0 chunk，刚加的项目知识库 SOP 也 0 次。**能力先于需求**，先观察，不要继续扩。
- **死扩展点/半成品**：`Skill` 扩展点 0 消费；`adopts.routes` 前后端都没人查；`network.go` 预置了飞书域名但没有 adapter；`secrets:*` 权限有文案没能力；前端 4 个 `notImplemented` 扩展点；`docs/plugin-api.md` 里的 `shell.openDrawer` 示例根本不存在。**要么标 experimental/删除，要么实现——「文档承诺 > 实现」会逐渐消耗对平台的信任。**
- **设置页 16 个分节，约一半是有界面无数据**（shortcuts/skills/webhooks/kb/browser allowlist 等）。合并为 4 组：连接 / Agent 与执行 / 插件与工作台 / 数据与备份。

### 5.3 无法默认关闭的根源

`plugins` 表 9 个全部 `installed=1`、7 个 `enabled=1`；清单**没有 `default_install` 之类字段**，也没有按插件裁剪构建的手段。所以「按需安装」目前等于「装完再手动关」。这是「不必要功能」会持续堆积的机制性原因——**需要一条「默认包 vs 可选包」的产品线，而不只是代码里的 9 次 `plugins.Add`。**

## 7. 优化路线（收益/成本排序）

### P0 · 2–4 天，先让产品「自洽」（不做信任会掉）

   - 顺带修「今日页数字」与「通知」两套口径的重复实现（同一件事在今日卡片、通知、任务列表各算一遍）。

## 8. 三条最该做的事（如果只能做三件）

1. **把「注意力」做成一个功能**：通知中心 + 今日口径 + 存量分诊两段式 + 跟踪字段自动补全。工作台的第一价值是「告诉我今天做什么」，现在这一条不成立。
2. **把默认包和可选包分开**：9 个插件全编进一个二进制、全部默认安装，是功能面失控的机制根源；trade/video/浏览器/旧前端/原型是明确的减法。
