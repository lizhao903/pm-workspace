# 产品工作台（pmw）产品评判

评判日期：2026-09-15 · 依据：源码实读 + 计划文档比对 + 线上库 `data/pm.db` 实测 + 实跑测试（`go test ./...` 全绿）+ 实机界面走查（截图归档 `~/pmw-ux-review/`）

---

## 摘要

以初衷为标尺评判，结论比单看功能清单更清楚。

初衷是：**Agent 与人从不同渠道收集汇总需要进行的任务，然后进行跟踪。**这是一个三段链条——收集、汇总、跟踪。项目现有框架由「产品经理视角」的计划文档形成（已实施），「项目经理视角」的部分仍在畅想（未实施）。这两个视角恰好对应链条的两端：产品经理视角解决收集与汇总，项目经理视角解决跟踪。

实测结果：**收集入口与汇总结构都建好了，但只发生过一次收集；跟踪的载体建好了，跟踪行为是零次的。**

- 收集：81 个对象全部来自一次经 MCP 的批量导入，`manual` 创建的 20 个已全部软删——手工录入无一存活。多渠道接入（IM、邮件、URL 抓取、会议纪要抽取）均未实现。
- 汇总：分类树使用率 100%（唯一被认真用的组织维度），标签 98 条；但自动归类、相似需求合并、持续去重都没有，汇总是一次性的人工整理。
- 跟踪：到期时间 1/81、负责人 11/81、状态修订 6 条、关联 15 条、`task_runs` 0 次。看板、日历、时间线这些**跟踪界面已经备好，却没有可跟踪的节奏**。

一句话：**库建好了，节拍没有。**

## 一、以初衷为标尺：三段链条实测

### 1.1 收集：单渠道，且是一次性的

| 渠道 | 实现状态 | 实测用量 |
|---|---|---|
| 人工界面新建 | 已实现（快捷捕获 C / 新建） | 19 条 manual + 1 条 inbox，**已全部软删** |
| 批量导入 | 已实现（`source=import`） | 81 条，当前全部存活 |
| Agent 写入（MCP） | 已实现，9 工具含 3 个写工具 | 81 条创建的 revisions 来源均为 `agent` |
| IM 转发（Slack / 飞书 / 微信） | 未实现 | 0 |
| 邮件 | 未实现 | 0 |
| URL 抓取正文 | 未实现 | 0 |
| 剪贴板 / 全局快捷键 | 仅有页内 Cmd+K，无系统级捕获 | 0 |
| 会议纪要抽取待办 | 未实现 | 0 |

「多渠道」目前等价于「人工整理后批量导入一次」。真实的工作方式可见于数据：需求散落在 Confluence 与 Google Docs（两者就在快捷访问页的外链里），人工整理成表后经 MCP 一次性导入。**缺少的是持续性的渠道接入**——一次性导入不是渠道，是搬运。

### 1.2 汇总：结构完整，自动化缺失

已有的汇总结构质量很高：6 类工作对象 + 两层分类树 + 交叉标签 + 5 种关联关系 + 优先级/负责人/到期字段。分类树使用率 81/81，是唯一被认真使用的组织维度。

缺的是让汇总「自动发生」的机制：

| 能力 | 状态 | 后果 |
|---|---|---|
| Inbox 分流 | 有 Inbox 状态与 4 条数据 | 有入口无分流动线 |
| 自动归类 | 未实现 | 81 条全靠人工挂分类 |
| 相似/重复需求发现 | 关系类型 `duplicates` 已定义，无自动召回 | 全库仅 1 条 duplicates |
| 汇总节奏（日报/周报汇总） | 未实现 | 导入之后没有任何汇总动作 |

### 1.3 跟踪：这是缺的一半

跟踪所需的**字段与界面都已存在**：状态集、优先级、负责人、到期（含「整天」语义）、看板拖拽换状态、今日/本周/逾期/停滞五档聚焦、`revisions` 字段级审计、`counts.stalled`（14 天未更新）口径。

缺的是让跟踪**产生动作**的三件事：

| 缺失 | 说明 |
|---|---|
| 调度器 | 无定时任务：逾期扫描、日报周报、自动快照、Agent 定时分析 |
| 通知/推送 | 顶栏通知只是一个数字角标，无点击行为；无桌面/邮件/IM 推送 |
| 流转与提醒规则 | 状态机可配置（允许的流转路径）未做；到期提醒、停滞提醒未做；周期任务未做 |

实测印证：这套字段几乎没被填——到期 1/81、负责人 11/81、状态修订 6 条。**跟踪不是「功能没做」，而是「行为没发生」**；而行为没发生的原因是没有节拍（没人/没有东西在固定的时间点催）。

### 1.4 两个视角的对应关系

| 视角 | 计划文档 | 对应链条 | 实施状态 |
|---|---|---|---|
| 产品经理 | `feature-analysis.md`、`layout.html`、`settings-enums.md`、`shortcuts-spec.md` | 收集 + 汇总 | 已实施，构成现有框架 |
| 项目经理 | `pm-gap-analysis.md`、`spec-baseline.md` | **跟踪** | 畅想，未实施 |

由此得到一个重要修正：**项目经理视角的那批能力（RAID、决策记录、变更控制、里程碑、度量看板、容量与干系人）不是「额外功能」，它们正是「跟踪」的具体形态。**「跟踪没做」与「项目经理视角没实施」是同一件事的两种说法。

## 三、功能盘点

### 3.1 已落地（代码存在、有测试、实机可用）

**数据层**：单表多态 `objects`（6 类对象，新增类型是数据不是代码）；分类树（物化路径、子树查询、级联移动、防自环、颜色继承）；标签；关联（5 种关系含反向显示名）；字段级修订历史；9 个迁移 + sha256 校验和（0005 起生效）；软删除 + 回收站 + 恢复。

**接口层**：70 条 REST 路由；统一响应信封、错误码映射、PATCH 三态语义；可配置枚举字典（优先级与关联关系从硬编码变为数据，停用而非删除）；8 种批量动作。

**界面**：三栏 shell、三档响应式、深浅色；列表 / 看板 / 表格三视图真实可用，日历与时间线为占位；详情抽屉 5 Tab（详情 / AI 助手 / 执行 / 活动 / 关联）；命令面板、快速捕获、全局快捷键；快捷访问独立页（外链 / 内跳 / 动作三种目标 + URL 变量替换）；设置页七页含类型编辑器与状态集可视化编辑。

**Agent 相关**：三类供应商（OpenAI 兼容 / Gemini / Ollama）、SSE 流式、密钥出口脱敏；内置对话 5 工具；MCP server 9 工具（6 读 3 写，走 HTTP 不直连 DB）；Claude Code 执行器（SSE、进程组取消、默认只读、输出落库）。

**运维**：迁移 checksum 查看、`VACUUM INTO` 快照、导出 JSON / Markdown（排除密钥表）；本地域名与 HTTPS（hosts + pf + mkcert + LaunchDaemon）。

## 五、界面走查

实机走查（1440×900，深色）。**界面完成度高于功能完成度**：信息架构清晰（侧栏只回答「在看哪类对象」，聚焦与回收站移入工具条），空态文案区分三种情形，破坏性操作有明确语义。

| 走查项 | 结果 |
|---|---|
| 列表 / 看板 / 表格 | 均可用。看板按状态分列（待整理 4 / 需求池 53 / 已排期 11）；表格列宽可拖拽 |
| 看板作用域约束 | 「全部类型」下不可用，提示需先选类型——合理但需自行发现 |
| 日历 / 时间线 | 占位，提示「将在 M2 支持」 |
| 详情抽屉 | 编辑能力完整（状态、优先级、负责人、到期含整天语义、分类、项目、工作区含继承提示、标签、正文、归档、删除） |
| 活动 Tab | 真实可用：「me 5 小时前 · Agent 创建了该对象」，Agent 归属准确 |
| 执行 Tab | 安全默认到位：未设工作区时给前置引导；「允许修改文件」默认不勾；空态诚实 |
| 设置页 | 七页完整；不可改字段逐项说明原因；迁移 checksum 表如实暴露 0001-0004 空值 |
| 数据与备份 | **只提供「立即快照」**——界面层证实无定时备份 |
| 快捷访问页 | 仅次于需求池的第二大真实使用能力：3 个外链（NS系统、Acme 任务反馈、Confluence）+ 1 个内跳动作 |

**走查新发现两条：**

1. **抽屉「AI 助手」Tab 是静态样稿，样稿含虚构数据。** 渲染了一段示例问答（「这条 REQ-0045 这周的进展怎么样，有风险吗？」→「本周 2 个子任务完成，权限矩阵任务已停滞 9 天…」）与一张「Agent 建议（草稿，需确认）」卡片，按钮全部禁用；而底部 Agent dock 真实可用。样稿用的是**真实编号 REQ-0045** 配虚构进展。项目内知道这是占位，但对外部读者与外部 Agent 会像「能力已具备」——建议样稿去掉真实编号，或直接删掉。
2. **顶栏通知按钮是死入口。** 有 `title`（待处理：逾期 N · 停滞 M）与数字角标，样式可点击，但无任何点击行为。

**检索实测（重要）：**

| 查询 | 命中 |
|---|---|
| 支付 / 企业 / 权限 / Stripe | 4 / 10 / 2 / 1 |
| 权限分权 / 权限 分权 / 支付 Stripe | 0 / 0 / 0（库中确有「Tab 级权限与授权类型分权」） |

缺陷是**查询语义**而非索引类型：`LIKE` 做单一连续子串匹配，无分词、无多词 AND/OR，中文用户最自然的检索方式必然得零。换 FTS5 trigram 只提升单串匹配性能，不解决多词；真正要补的是查询词拆分 + AND/OR。

## 六、做对的判断

**1. 数据模型的抽象层级选对了。** 单表多态 + 分类树 + 万物关联 + 字段级修订，使 RAID、ADR、里程碑、干系人全部只需注册新类型——这正是「产品经理视角的框架」能在低改动下延伸到「项目经理视角」的前提。项目的关键判断在这一层已经做完，后面缺的是填充，不是重构。

**2. 契约防呆的密度罕见。** 路由表与 API 文档双向守卫、`domain → API → store` 三段各配反射测试、`counts` 与列表口径逐字一致。这类投入不产生功能，只防止「悄悄算错」——而悄悄算错正是长期工具最致命的失效模式。

**3. 安全边界的克制优于同类个人工具。** 密钥明文但出口全链路脱敏并写明取舍前提；MCP 刻意不暴露删除能力；执行器默认只读、勾选后才给 `--permission-mode acceptEdits`、任何情况下不用 `--dangerously-skip-permissions`；Agent 写盘越界在写盘前堵死。

**4. 面向 LLM 的工具接口设计成熟。** 紧凑文本返回、状态渲染成 `进行中(doing)`、错误回喂模型、id 与 ref 双认、清空传空串、`due_at` 兼容模型真机输出的四种无时区格式。这是「人机双渠道」能成立的技术前提，已经打好。

**5. 审计链路真实可用且归属准确。** 活动 Tab 正确显示「Agent 创建了该对象」。多数自建工具写了审计但不呈现，这里两头都做了。

**6. 跟踪的界面已提前备好。** 看板（拖拽换状态）、日历、时间线、今日/本周/逾期/停滞五档聚焦、`counts.stalled` 口径——跟踪所需的呈现层其实已经就位，缺的是驱动它的机制。这意味着「跟踪」不需要从零开始。

## 七、问题（按严重度）

### P0-1 数据无自动备份
`POST /api/admin/snapshot` 存在，界面只提供「立即快照」，无任何定时器调用。81 个真实对象只存在于 `data/pm.db` 一个文件，而 `data/` 不入版本库。这是当前唯一可能造成不可逆损失的问题。

### P0-2 跟踪链条完全缺失（初衷的另一半）
调度器、通知、流转与提醒规则全部未做，导致字段建了没人填（到期 1/81、负责人 11/81）。这直接命中原初目标：**「收集汇总后跟踪」的跟踪没有发生**。界面已备好，缺的是驱动机制与节拍。

### P1-3 收集仍是一次性搬运，不是渠道
多渠道接入（IM / 邮件 / URL 抓取 / 系统级捕获 / 会议纪要抽取）全未实现。当前唯一有效渠道是「人工整理后经 MCP 批量导入」，这意味着**收集的质量与频率完全取决于人是否主动整理一次**——实测只发生了一次。

### P1-4 内置 Agent 悬空，且缺两道自证必要的前提
内置对话有 5 个工具，但写操作直接落主表（无草稿、无人在环），检索无任何知识分层，也无运行记录与成本核算。已配置 2 个供应商，实际只跑过一次「hi」；执行器 0 次调用——用户已用外部 Claude Code + MCP 替代。

真正的问题不是「内置 Agent 不好用」，而是它与初衷的关系没被定义清楚：**初衷要的是「Agent 与人两个渠道」，而 Agent 的能力价值最大化场景恰恰是跟踪**（主动发现停滞、自动汇总周报、按时推送），不是再开一个聊天框。当前把 Agent 做成了对话入口，而它应该做成**提醒源**。

### P1-5 无鉴权，且已暴露到域名
只靠绑定 `127.0.0.1`，但已通过 hosts + pf 可用 `https://bro.vip` 访问；MCP 又让任意 Claude Code 会话都能改库。同时 `objects` 表只有 `owner TEXT`，未预留 `owner_id` 与权限层——一旦手机访问或多端同步进入路线，这是重构级改动。

### P1-6 检索在多词场景下必然失效
实测「权限 分权」「支付 Stripe」均返回 0，而库中存在匹配内容。

### P2-7 汇总自动化缺失，人工成本不可持续
81 条全靠人工挂分类，相似需求无召回（全库 1 条 duplicates），无汇总节奏。数据量再翻一倍时，维护成本会超过收益。

### P2-8 功能面过剩，洞察为零
6 类对象、5 种视图、8 种批量动作、完整字典管理、三种跳转目标的快捷体系都在，而只有「需求池 + 分类 + 标签 + 快捷访问」在用。`revisions` 全表 135 条足以算出停滞项、周期时间、状态停留时长——**一个都没被产品消费**。

### P3-9 界面细节
抽屉 AI 助手样稿含真实编号配虚构数据；顶栏通知按钮是死入口；列表行删除按钮实际语义为「移到回收站」，标签与行为不完全一致；状态栏与设置页的文件体积口径不一致（308 KB vs 388 KB）。

### 关于「文档与实现脱节」的修正
四份计划文档（`pm-gap-analysis.md`、`spec-baseline.md` 等）是**明确定位的畅想与设计**，项目内清楚它们未实施，因此不构成本次问题。唯一建议是为文档加一个「实现状态」标记，避免外部读者或外部 Agent 误判。原评判中把它列为 P0 是将「未标记」误读为「未说明」，此处修正。

## 八、优先级建议

以初衷为标尺重排。核心判断：**不要先补项目经理视角的完整方法论，先把「跟踪」这条腿接上最小的可运转闭环。**

**立即（不做则信任崩塌）**
1. 给 `snapshot` 接定时器，快照落 `~/pmw-snapshots/` 并轮转。工作量极小，风险消除最大。
2. 把未实施的东西标清楚：抽屉 AI 助手样稿去掉真实编号或删除；顶栏通知按钮要么接上行为要么去掉可点击样式；计划文档加实现状态标记。

**短期：最小跟踪闭环（这是初衷的另一半，也是唯一不可替代的部分）**
3. **调度器 + 提醒推送**。数据源全部就位：`counts.stalled`（14 天）已实现、`revisions` 可算停留时长、到期字段已有。先做两件事：每日扫逾期与停滞、每周自动生成一份变更摘要。推送通道可先用桌面通知 + 一个可被外部 Agent 读取的接口。
4. **让 Agent 成为提醒源，而不是聊天框**。把「发现停滞、汇总周报、按时催办」做成 MCP 工具或定时任务，让人在外部的 Claude Code / WorkBuddy 里被动收到判断。这条同时解释了内置 Agent 的存在理由——也解释了为什么它现在没人用：它被做成了需要用户主动打开的入口。
5. **降低跟踪字段的录入成本**。到期 1/81、负责人 11/81 说明格式化的跟踪字段是负担。让 Agent 在导入/创建时给出建议值（甚至直接补全），比要求人手工填更现实。

**短期：检索语义**
6. 查询词拆分 + 多词 AND/OR（当前唯一会影响日常使用的功能缺陷）。

**中期：跟踪的载体扩展（视最小闭环是否被真实使用再决定）**
7. 状态机可配置（允许的流转路径）。
8. 周期任务（每周一、每月末这类例行工作）。
9. 项目经理视角台账按「使用概率」排序分批做：先 RAID（风险/问题，最贴近日常跟踪），再决策记录，最后变更控制与里程碑。**每一批做完先观察是否被用，再决定下一批。**
10. 度量看板（周期时间、状态停留时长、按时交付率）——全部可从 `revisions` 算出，成本低、能验证「跟踪是否真的在发生」。

**待验证再投入**
11. 收集渠道接入：优先 IM 转发（Slack / 飞书）与会议纪要抽取待办，因为这两处是需求最自然的产生地。URL 抓取、系统级捕获次之。
12. 汇总自动化：相似需求召回 + 自动归类建议。
13. Saved View、日历、时间线、关联图：待跟踪闭环跑起来后再做，否则仍是一批空转的界面。

**重构级决策（需先拍板）**
14. 鉴权与 `owner_id`：只要手机访问或多端同步进入路线，必须先在数据层补。

**不建议现在做**
15. 人在环草稿机制：内置 Agent 尚无实际使用，先解决「Agent 该干什么」，再解决「Agent 写错了怎么办」。若确定保留内置 Agent 的写能力，则此项升为 P0。
16. `specs` / `spec_versions` 基线治理四张表：它是为解决「Agent 读到废弃方案」而设计的，而当前 Agent 读的还是 LIKE 检索、库里也还没有多版方案。等方案库真的出现多版本再建。

## 九、结论

以初衷为标尺，这个产品造出了那条链条的前三分之二，且造得相当扎实：数据模型可扩展、契约防呆严格、Agent 接口成熟、跟踪界面已备好。**真正缺的是最后一环——让跟踪发生。**

而且缺的不是功能，是节拍：字段都在，界面都在，没有人或没有东西在固定的时间点催。

所以下一步最该做的不是补项目经理视角的完整方法论（RAID、变更控制、里程碑、度量那一整套），而是先用最小成本把节拍立起来：**每日扫逾期与停滞、每周出一份变更摘要、让 Agent 主动把判断推给人。**

节拍一旦立住，项目经理视角的那些台账才有被填的动力——否则它们只会是第二批空转的界面。

三条最该做的事，按顺序：**接上备份定时器 → 让 Agent 变成提醒源（每日扫停滞 + 每周摘要）→ 拆查询词修检索**。
