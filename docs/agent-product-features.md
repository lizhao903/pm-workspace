# 产品视角：把「其他 Agent」纳入产品需要建哪些功能

2026-09-15 · 视角：产品经理 · 目标：让平台上「调用不同 Agent 同步实现工作任务」成为可日常运转的能力

---

## 一、先立定位判断

**平台不做最强的 Agent，平台做 Agent 的调度台、档案室与记分板。**

三件事各自的责任边界：

| 角色 | 平台负责 | 不负责 |
|---|---|---|
| 调度台 | 知道有哪些 Agent、谁能干什么、把活派给谁、盯住干得怎么样 | 不追求自己的 Agent 比外部强 |
| 档案室 | 每次执行的输入、过程、产出、成本都留档并归位到对象上 | 不存 Agent 的私有上下文 |
| 记分板 | 谁靠谱、哪种活该给谁、钱花在哪 | 不做 Agent 内部的提示词调优 |

**现状错位要正视**：当前把 Agent 做成了**对话框**（底部 dock，等用户主动打开），而它应该被做成**工位**（有活就派过去，干完把东西交回来）。实测证据：内置对话只跑过一次「hi」，执行器 0 次调用——不是功能不好，是**形态错了**，用户没有理由去打开一个空的聊天框。

**产品里目前没有「Agent 是谁」这一层。** `agent_providers` 是模型接入点（一个 API 地址 + 密钥），不是 Agent。缺这一层，就回答不了用户最基本的问题：**这件事该找谁做。**

补一句设计依据：侧栏「Agent 中心 2 运行中」在布局线框稿里就画过，属于早期设计意图，只是从未实现。

## 二、把 Agent 变成一等对象（花名册）

### 2.1 Agent 目录页
一个独立页面（不是设置里的一个表单），回答四个问题：

| 用户的问题 | 页面要给的答案 |
|---|---|
| 我有哪些 Agent？ | 列表：内置 / 本机 CLI / 外部接入，同一张表 |
| 各自能干什么？ | 一句话能力描述 + 能承接的对象类型 + 擅长产出（文档 / 字段变更 / 报告 / 代码） |
| 现在能不能用？ | 状态：可用 / 忙碌 / 离线 / 超配额 / 已停用 |
| 干得怎么样？ | 本周接活数、成功率、平均耗时、平均成本（详见第五节记分卡） |

### 2.2 能力声明（派单的前提）
每个 Agent 声明两件事：**能承接什么**（对象类型、标签）与**擅长什么**（工作性质：写作、研究、工程、分析、事务）。

有了它才能做到两件现在做不到的事：
- 派单时给出推荐：这条需求 → 推荐 3 个 Agent + 推荐理由（擅长领域匹配、历史成功率、当前负载）
- 支持「按能力自动分配」：批量派单不用逐个挑 Agent

### 2.3 Agent 的版本与配置档案
提示词、模型、参数可改，但每次改动留版本。目的很具体：三个月后要能回答「这批周报是哪个配置生成的」，以及「改完配置后产出质量是变好还是变差了」。

配置项还应包含：每日接活上限、单次成本上限、默认产物目录（复用现有 `workdir` 的对象→项目继承逻辑）。

## 三、派发：把「找谁干活」变成三秒动作

### 3.1 三个派单入口，覆盖三种真实场景

| 场景 | 入口 | 交互 |
|---|---|---|
| 我看到这条需求，想让它做点什么 | 详情抽屉 | 选模板 → 选 Agent（默认给推荐）→ 看预览 → 派 |
| 我有一批同类的活 | 列表批量 | 勾选 N 条 → 选模板 → 「按能力自动分配」或指定同一 Agent |
| 这类活以后都要这么办 | 流水线 | 作用域 + 步骤里配置 Agent 与模板，之后自动持续派 |

### 3.2 任务模板库（提效的真正杠杆）
把高频工作固化成模板，用户不再写提示词：

首批建议：需求结构化、写 PRD、竞品调研、周报汇总、会议纪要抽待办、需求去重判定、风险识别。

每个模板要带三样东西，否则用户不知道什么时候该用它：
- 适用场景说明（一句话）
- 产出示例（让人先看到结果长什么样）
- 预期产出类型（写文件 / 改字段 / 出报告）

**最重要的一条功能：支持把一次成功的执行「存为模板」。** 这是模板库能持续变好的唯一机制——好结果从实践中来，不是从设计中来。

### 3.3 派单前的上下文预览（信任的前提）
不能只发 `{{title}}` 就完事。实际要装配：对象全字段 + 关联对象摘要 + 所属项目上下文 + 该对象最近的修订。

但**必须提供预览**：派单前能看到"将要发送给 Agent 的完整内容"，并且可以就地编辑再发。

这一条同时解决两个问题：用户敢把活交出去；出问题时能立刻判断是"上下文给错了"还是"Agent 做错了"。

### 3.4 依赖与任务链
支持「PRD 写完后自动派评审 Agent」。产品上表现为一条**任务链**视图：能看到链上每一环的状态与产出，而不是一堆互不相关的任务。

## 四、可见：运行中心与诚实的状态

### 4.1 运行中心（Agent 中心的主 body）
一张列表容纳平台内与外部两种执行，状态归一：排队中 / 执行中 / 等待确认 / 失败 / 停滞 / 已完成。

每条可下钻到：过程步骤、工具调用、产出文件、耗时、成本、关联对象。空闲时它也是一屏「当前在跑的活」——掌控感就来自这里。

### 4.2 状态语义必须诚实（这是产品态度问题）
- 外部 Agent 断联 → 显示「**失联**」，不显示「执行中」
- 发出取消请求 → 显示「**已请求取消**」，不显示「已取消」
- 失败 vs 部分成功分开呈现（现有 runner 已有「被权限挡下但绕路做成」的判定逻辑，可直接复用）

含糊的状态比错误的状态更糟：用户会据此做出错误决定。

### 4.3 中断与接管
- 卡住的活能取消（复用已有的进程组 kill）
- **失联的活能接管**：改派给平台内队列、改派给另一个 Agent、或转人工
- 这一条常被忽略，但在真实使用里一定会遇到——外部工具挂了、网络断了、Agent 卡在某个循环里

## 五、归位：产出必须回到对象上

### 5.1 产出区
每个对象的详情抽屉里有一个「产出」区：该对象历史上所有 Agent 产出（文件、结论、字段变更建议），可预览、下载、在 Finder 打开。

现在的状况是产出散在 workdir 里没人看——Agent 干了活，价值没落回业务对象。

### 5.2 产出转正
- 一键把产出沉淀为 `doc` 对象，并自动建立 `references` 关联回源对象
- 正文级产出可直接写回对象 body（走「建议」态）

### 5.3 人工确认与**拒绝原因回流**
Agent 对状态 / 负责人 / 正文三类字段的写入走「建议」态，提供接受 / 编辑后接受 / 拒绝。

关键细节：**拒绝时给一组快捷原因**（方向不对 / 粒度太粗 / 事实错误 / 缺上下文 / 不需要），并把原因喂回该 Agent 的下次派单提示词。

这一条是「Agent 越用越准」的唯一闭环，也是当前设计完全缺失的一环。没有它，改进只能靠人反复调提示词。

## 六、择优：记分卡与成本

### 6.1 Agent 记分卡
| 指标 | 用途 |
|---|---|
| 成功率 | 判断可靠性 |
| 平均耗时 | 判断能否用在赶时间的活上 |
| 平均成本 | 判断值不值得派 |
| **人工返工率**（产出被拒绝或编辑后接受的比例） | **最有价值的指标**——它衡量的是"这个 Agent 干完我还得改多少" |
| 按模板分组 | 哪个模板的产出最常被直接接受 |
| 按对象类型分组 | 哪类需求适合派给谁 |

### 6.2 成本与配额
每次运行的 token 与成本入库；按 Agent / 模板 / 项目 / 时间聚合。支持每日每月上限，超限转排队或告警。

### 6.3 结果对比（关键节点用）
同一任务派给两个 Agent 跑，产出并排比对，采纳其一。只用在关键节点（方案、竞品结论），不必常态使用——否则成本翻倍且决策负担变大。

## 七、编排：让多个 Agent 接得上

### 7.1 流水线里作为一个步骤
Agent 执行是流水线的一种步骤类型（详见 `design-pipeline-agent.md`），可与改字段、通知、建对象、汇总等步骤串联。

### 7.2 接力传递
上一个 Agent 的产出作为下一个的输入，而不是让下一个重新读一遍对象。产品上表现为「接力」：能清楚看到交接点与传递了什么。

### 7.3 多 Agent 并行
同一批对象分给多个 Agent 并行处理（如 20 条需求分给 3 个 Agent），在运行中心看到的是一个批次而非 20 条孤立任务。

## 八、治理：接入、配额、诊断

### 8.1 接入零摩擦
外部 Agent 接进来三步：拿到地址与令牌 → 声明能力 → 开始接活。配套一个「自检」：连通性、能力声明是否合法、能否成功拉取到任务。

### 8.2 外部 Agent 的任务箱
外部 Agent 侧看到的应该是一个任务箱：认领、执行、上报。同时支持**反向接入**——外部 Agent 自己发起的执行也能上报进平台被监控，不强制必须经平台派单。这才符合「多个渠道都会执行」的实际。

### 8.3 诊断视图
每个 Agent 的最近失败按原因分类（网络 / 凭据 / 参数 / 上游限额 / 权限），并给一个「为什么这个 Agent 最近不干活了」的结论视图。

## 九、优先级（按提效杠杆）

| 级别 | 功能 | 为什么排这个位置 |
|---|---|---|
| **P0** | Agent 目录 + 能力声明 | 没有它，后面所有派单、推荐、编排都无从下手。且它是产品当前完全缺失的一层 |
| **P0** | 任务模板库（含"存为模板"） | 提效的真正杠杆：把提示词工作一次性做完，之后一键复用 |
| **P0** | 派单三入口 + 上下文预览 | 用户敢把活交出去的前提 |
| **P0** | 运行中心（内外部统一） | 「同步执行」的落点：多 Agent 并行时人只需要看一个面板 |
| **P0** | 产出归位到对象 | 否则 Agent 干了活，价值不落回业务 |
| **P1** | 拒绝原因回流 | Agent 越用越准的唯一闭环 |
| **P1** | 记分卡（尤其人工返工率）+ 成本配额 | 决定"该找谁"与"值不值得" |
| **P1** | 依赖 / 任务链 | 让多个 Agent 接得上，而不是各干各的 |
| **P1** | 失联接管 + 接入自检 | 真实使用里必然遇到，前期不补后期必踩 |
| **P2** | 结果对比 | 关键节点有价值，但成本翻倍，先不用 |
| **P2** | 接力传递、诊断视图 | 等多 Agent 日常化之后再补 |

## 十一、一句话结论

要做的事情可以概括为：**给 Agent 建一份花名册、一套派单方式、一个监控面板、一条产出归位通道、一张记分卡。**

其中只有两件是「新造」，其余都是把已有能力换个形态接上：**花名册与能力声明**（产品当前完全缺失的一层），以及**拒绝原因回流**（让 Agent 越用越准的闭环）。其余功能在数据层与执行层都已有依托。

最重要的一个产品判断是：**把 Agent 从「对话框」改成「工位」** —— 它不该等用户来打开，而该在活出现时被派过去，干完把东西交回对象上。
