已修复：逾期语义按天互斥

Overdue 原本定义为 due_at < now，导致「今天早些时候已过到期时刻」的对象 同时算今日和逾期——同一条数据上午在「今日」、下午跳到「逾期」。 改成 due_at < 今天00:00 后两者按天互斥，且与一天中的时刻无关。 分界抽成 overdueBefore() 供 counts 与 objects 共用，口径不会再漂。 实跑验证：今天凌晨 1 点到期的对象 today=1 overdue=0。

这个缺陷是被一条「上午跑绿、下午跑红」的测试暴露的。我们当初修「今日/逾期重叠」时 只解决了「上界扫进往日」那一半，加总断言设计是对的，但测试数据选在了非边界值上。

八、关键设计决定 为什么这么做

决定理由代价 / 边界
单表多态工作对象 RAID 台账、ADR、里程碑、干系人全部只需注册新类型，零代码 跨类型查询要带 type 维度，状态集按类型隔离
字段级修订历史 日报周报的数据源；周期时间、状态停留时长等度量全从它算 写入量翻倍，但个人工具量级可忽略
枚举停用而非删除 删掉被引用的枚举值会留下悬空数据，界面出现无名无色的孤儿值 需要引用计数接口；key 一经创建不可改
Agent 只能读 canonical 层 过程产物与当前基线混在一起，RAG 会把废弃方案当现行设计 要维护基线版本，人工确认才能升为 canonical
MCP 走 HTTP 不直连 DB 复用 API 层全部校验；避免两个进程写同一个 SQLite 工作台必须在跑
密钥存明文，防线在出口 本地单人工具，引 keychain 会带来「密钥丢了库打不开」的运维负担 库要共享或同步上云时此取舍必须重做
pf 重定向而非监听 80 监听 80 要求整个进程跑 root，一个本地工具没必要 需要一次 sudo；pf 规则要 LaunchDaemon 保持

九、风险与欠账

版本控制已建立（本地）

首次提交 78536d4，172 个文件，分支 main，无远端。 已实测：全新克隆能直接 go build 通过——internal/webui/dist/ 的占位 index.html 保住了 go:embed 对「目录非空」的要求。data/ 不入库（真实数据，且含明文 api_key）。

数据本身仍无自动备份

git 保护的是源码，不是那 81 个工作对象。/api/admin/snapshot 存在但没有任何东西定期调它， 快照全靠手工。原先快照放在 /tmp/pmw-snapshots/——macOS 会在重启时清空 /tmp， 已复制一份到 ~/pmw-snapshots/。真正的解法是给 snapshot 接一个定时器。

无鉴权

只靠绑定 127.0.0.1。局域网访问、手机访问、以及 MCP 让任意 Claude Code 会话都能改库——三件事都以此为前提。

检索是 LIKE 不是全文索引

数据量小时无感，上千条之后中文检索会明显吃力。FTS5 的 trigram 分词方案在 M2。

0001-0004 迁移不受校验保护

它们是在 schema_migrations 加 checksum 列之前应用的，库里记的是空串，启动校验直接跳过。 0005 往后才真的锁住。那四个文件改了不会被发现。不打算补——回填 checksum 等于把「现在的样子」 追认成「当初应用的样子」，是假装验证过。/api/admin/migrations 已把空 checksum 如实暴露。

等用户决定的三件事

回收站里 20 个软删除的工作对象（恢复还是清空）· TLS 证书（五条手工命令，从 brew install mkcert 起）· 版本控制（见下）。

一行从写下那刻就是错的注释

cmd/pmw/main.go 原来写 WriteTimeout: 60 * time.Second, // 给将来的 SSE 留余量。 WriteTimeout 不是「写一次卡住多久算超时」，是从开始写响应那一刻起的绝对截止时间—— 对 SSE 等于给整条流设了硬上限，注释说的和代码做的正好相反。

它不留痕迹：响应头早就发出去了，访问日志照样记 200，服务端没有任何 WARN， 只有浏览器那头看到 network error。伤得最重的是任务执行线——跑本机 Claude Code 超一分钟是常态，等于每个长任务都在一分钟整断流，而日志一片祥和。 今天几次执行测试恰好都在 35 秒以内，所以一直没撞上。

实测：改前 70s / 81s 两次都断；改后 77 秒、1301 个 delta、正常收到 done。 这行从首次提交起就在，git log 里没人动过。 过期的注释还能靠「和代码对不上」发现；这种从写下那刻就错、读起来又完全合理的，只能靠真跑撞出来。

本轮反复出现的失效模式

「数字错了不会崩溃，只会让人用错的数字做判断」——徽标与列表口径不一致出现三次、筛选参数被静默丢弃出现三次。 现在三步链条各有反射测试把关，且都用反证验过自己真会红。这是本轮比修好的 bug 更值钱的产出。

今晚又添四种，全部已堵：MCP 发着一个已经不存在的参数（API 只认 owner_id， MCP 还在发 owner，未知 key 被静默忽略——按人名筛返回全量、改负责人无声失败， 而这个 MCP 已经配进用户的 Claude Code 了）；.gitignore 逐条列举漏掉了子目录 （/data/*.db 盖不住 data/backups/，那里是含明文 api_key 的全量副本， 一次 git add -A 就进 git 历史）；新克隆 build 通过但跑起来白屏 （提交的 dist/index.html 引用着不入库的 assets——「构建通过」看上去一切正常）； 契约写哈希、实现是定值（头像五个人同色，而假数据自测时人人有颜色，这条分支走不到）。

再往前三种：文档跟代码脱节（不参与编译，烂掉只表现为有人照着它写调用）、 替身比真实现宽松（测试永远绿，问题只在生产出现）、 反证本身假绿（删代码导致编译失败，那是编译错误不是断言失败）。前两种已加守卫，第三种只能靠人记着。

协作上踩的两条：多 agent 同时改一个仓库时跑 git add -A，等于替别人提交他写到一半的代码； pkill -f vite 这类模式匹配杀进程会带走别人正在验证的服务器，而对方只会看到「它莫名其妙没了」。 两条都已发生，按路径 add、按端口 kill。
